2Introduction

2.1 Purpose

This document defines, in a single controlled artefact, what the Local Voice Chatbot system does, how it is constructed, how its behaviour has been verified, and what its residual risks and limitations are. It serves three functions: as a specification against which the delivered implementation can be assessed; as a design record explaining why each significant technical decision was taken; and as an evidence dossier presenting the measured results that support or, in one important case, refute the system's design hypotheses.

2.3 Scope

2.3.1 In Scope

  • Real-time speech capture with automatic endpoint detection, on a single local machine.
  • Offline speech-to-text with GPU acceleration and automatic CPU fallback.
  • Confidence assessment of each transcription, with retry and explicit-rejection behaviour.
  • Response generation by a locally-hosted large language model, with multi-turn context.
  • Offline neural speech synthesis and playback of the generated response.
  • Two operator interfaces: a terminal client and a browser-based chat interface.
  • Tooling to record a personal evaluation dataset and to execute a reproducible accuracy benchmark.
  • Configuration management, automated testing, continuous integration, logging, and error handling.

2.3.2 Out of Scope

  • Authentication and authorisation. The system is designed for single-user operation on 127.0.0.1. It has no user accounts, sessions, or access control.
  • Multi-user or concurrent operation. One recogniser instance, no request queueing, no tenancy isolation.
  • Internet-facing deployment. Hosting the system publicly would contradict its core design premise (§15.1) and is explicitly not supported.
  • Packaging and distribution (installer, container image, signed release).
  • Wake-word activation, barge-in interruption, and speaker identification.
  • Languages other than English. Recognition is pinned to English; the synthesis voice is US English.

3Product Overview

3.1 Problem Statement

Speech recognition models are trained predominantly on conversational and read speech delivered at typical loudness, pitch, and rate. When a speaker departs from that distribution — whispering in a quiet room, raising their voice across a distance, deliberately slowing down for emphasis, or rushing — recognition accuracy falls. The operational hazard is not the accuracy loss itself but its failure mode: the model does not signal uncertainty. It emits a fluent, plausible, and incorrect transcription, which any downstream component will then treat as ground truth.

In a voice assistant this produces a characteristic and damaging user experience: the assistant answers a question the user did not ask, with no indication that it misheard. For command words in particular — stop, help — a silent substitution is a functional failure, not merely an annoyance.

A second constraint shapes the design. Voice data is among the most sensitive categories of personal data: it carries identity, emotional state, health signals, and whatever the speaker happens to say in their own home. Any architecture that transmits raw audio to a third-party service inherits an irreducible privacy exposure. This project therefore adopts a strict constraint: nothing leaves the machine.

3.2 Solution Overview

The system implements a five-stage pipeline in which every stage executes locally, together with a decision gate between recognition and generation.

CaptureMic + WebRTC VAD
›
PreprocessRMS normalise
›
Recognisefaster-whisper, GPU
›
Confidence gateaccept / retry / reject
›
GenerateOllama, local LLM
›
SynthesisePiper TTS
Figure 1. End-to-end processing pipeline. Every stage executes on local hardware; the only network traffic is loopback to 127.0.0.1. The confidence gate is the sole point at which the pipeline may decline to proceed and return control to the speaker.

The confidence gate is the architecturally significant element. Rather than forcing the recogniser to always produce an answer, the system treats "I am not sufficiently sure" as a first-class outcome: it re-decodes with a wider beam, and if confidence remains below threshold it asks the speaker to repeat rather than guessing. This mirrors how uncertainty is handled in production speech systems and converts a silent failure into a recoverable interaction.

3.5 Constraints, Assumptions and Dependencies

IDTypeStatement and consequence
CON-01ConstraintNo external network calls. Every component must operate against local files or loopback addresses. This eliminates cloud STT/LLM/TTS options entirely and drives the selection in §7.4.
CON-02Constraint4 GB VRAM budget, shared. The recogniser and the language model must be simultaneously resident. This bounds model sizes and mandates quantisation (§13.2).
CON-03ConstraintConsumer Windows host. Precludes deployment tooling that assumes Linux (e.g. gunicorn), and introduces the CUDA library resolution problem documented in §8.4.2.
CON-04ConstraintBrowser microphone access requires a secure context. getUserMedia is available only over HTTPS or on localhost; the latter is used.
ASM-01AssumptionA single speaker uses the system at a time, in a reasonably quiet environment.
ASM-02AssumptionThe operator has administrative rights sufficient to install the Ollama runtime.
ASM-03AssumptionUtterances are short — command words to single sentences. This assumption is material: §12.4 shows a design defect that arose precisely from applying a technique valid for continuous speech to isolated words.
DEP-01DependencyOllama must be installed and running, with the configured model pulled, before the pipeline can generate responses.
DEP-02DependencyA Piper voice model (.onnx plus .onnx.json) must be present at the configured path.
DEP-03DependencyGPU acceleration requires the cuBLAS and cuDNN runtime libraries; absent these, the system degrades automatically to CPU (§8.4).
