6.2 UC-01 — Conduct a spoken conversational turn

IdentifierUC-01
Primary actorSpeaker
GoalObtain a spoken answer to a spoken question, with no data leaving the machine.
PreconditionsService running; microphone permission granted; Ollama reachable; voice model present.
TriggerUser activates the microphone control and speaks.
Main flow 1. User starts recording; the interface indicates the listening state.
2. User speaks, then stops recording.
3. System decodes the browser audio to 16 kHz mono PCM.
4. System normalises amplitude (§8.3).
5. System transcribes the audio and computes a confidence score.
6. The confidence gate accepts the transcription (§8.5).
7. The transcription is displayed as the user message, annotated with its confidence.
8. System submits the transcription, prior turns, and system prompt to the language model.
9. Response tokens stream into the interface as they are produced.
10. On completion, the response is synthesised and played automatically.
11. The turn is appended to session history; the timing record is written.
PostconditionsConversation history extended by one exchange; one row appended to the confidence audit log; per-stage timings recorded.
Alternate flows A1 — Low confidence. At step 6 the gate rejects; control transfers to UC-02.
A2 — No speech detected. Capture yields insufficient voiced audio; the turn is abandoned and the system returns to listening.
A3 — Model server unreachable. At step 8, after bounded retries, a diagnostic replaces the response.
A4 — Synthesis failure. At step 10 the textual response remains displayed; playback is skipped and an advisory is shown.

6.3 UC-02 — Recover from a low-confidence transcription

IdentifierUC-02
Primary actorSpeaker
GoalPrevent an unreliable transcription from being acted upon, and give the speaker an explicit opportunity to repeat.
PreconditionsAn utterance has been transcribed with confidence below the configured threshold.
Main flow 1. The gate evaluates the first-pass transcription as below threshold and returns RETRY_MORE_BEAMS.
2. System re-transcribes the same audio at beam size 5 rather than 1.
3. The gate re-evaluates the second attempt.
4. If now at or above threshold, the transcription is accepted and UC-01 resumes at step 7.
5. Otherwise the gate returns ASK_TO_REPEAT; the transcription is not forwarded to the language model.
6. The interface displays the rejected text in a visually distinct form together with its score.
7. The system synthesises and plays a request for repetition.
8. Control returns to the speaker.
PostconditionsNo language model invocation occurred. Two rows are appended to the audit log — one per attempt — recording both scores, both beam sizes, and both decisions.
NotesThis is the principal safety property of the system. Correct operation was observed during system testing, including a case in which a non-speech input produced a spurious transcription at confidence −0.88 and was correctly refused (§11.5).

7System Architecture

7.1 Architectural Overview

The system is a layered monolith comprising a shared domain core and two interchangeable presentation layers. The core (pipeline.py and its collaborators) owns all domain behaviour; the terminal and browser front ends are thin adapters over it. This is deliberate: it guarantees that both interfaces exhibit identical recognition, gating, and generation semantics, because they invoke the same functions rather than parallel implementations of the same idea.

7.4 Technology Selection and Rationale

Every selection below was constrained first by CON-01 (no external network calls), which excluded all hosted services outright, and second by CON-02 (4 GB of shared VRAM).

Table 7.4 — Component selection, alternatives considered, and rationale
FunctionSelectedAlternatives consideredRationale
Speech recognition faster-whisper on CTranslate2; model small OpenAI whisper reference implementation; whisper.cpp; Vosk; hosted STT APIs Hosted services excluded by CON-01. The reference implementation requires the full PyTorch stack — several gigabytes of dependency and materially higher VRAM. CTranslate2 runs the same weights with lower memory and faster inference, and supports int8_float16 quantisation, which was decisive under CON-02. Vosk offers lower accuracy on this task.
Model runtime Ollama 0.33.3 llama.cpp directly; LM Studio; vLLM; Hugging Face transformers Ollama manages model acquisition, quantisation format, GPU layer offload, and memory residency automatically, exposing a stable local HTTP interface. vLLM targets server-class GPUs. Direct llama.cpp integration would have required manual CUDA build management for no functional gain.
Language model llama3.2:3b (Q4_K_M, 2.0 GB) qwen2.5:3b-instruct; 7–8 B parameter models Selected after direct comparison (§12.6). Larger models exceed the VRAM budget when co-resident with the recogniser. Between the 3 B candidates, llama3.2:3b was more reliably correct on elementary arithmetic and produced phrasing better suited to spoken delivery.
Speech synthesis Piper; voice en_US-lessac-medium Coqui TTS; espeak-ng; Windows SAPI Fast enough on CPU alone, leaving the GPU entirely to recognition and generation, while remaining natural enough for conversational use. espeak-ng is markedly more synthetic; Coqui carries a heavier dependency footprint. Licensing implications are recorded in §15.8.
Endpoint detection WebRTC VAD Fixed-duration recording; energy thresholding; Silero VAD Fixed durations either truncate long utterances or add latency to short ones. Energy thresholding fails on whispered input — a primary target condition. WebRTC VAD is well established, computationally trivial, and operates frame-by-frame at the required sample rate.
Signal processing librosa Hand-written DSP; torchaudio; scipy alone Provides tested implementations of pitch tracking, onset detection, and time-scale modification. torchaudio would reintroduce the PyTorch dependency deliberately avoided in recognition.
Media decoding PyAV Client-side WAV encoding; external ffmpeg binary Already present as a transitive dependency of the recogniser, so adds no install cost. Bundles its own FFmpeg libraries, avoiding a system-level dependency. Client-side encoding would have required hand-written resampling in JavaScript.
Web framework Flask; Waitress in production mode FastAPI; Django; http.server The HTTP surface is five endpoints; Django is disproportionate. FastAPI’s asynchronous model offers no benefit where the workload is bounded by synchronous GPU inference. Waitress was selected over Gunicorn because Gunicorn does not support Windows (CON-03).

Deployment note

The browser is the only component requiring a graphical session, and it connects to localhost. Because getUserMedia treats localhost as a secure context, microphone access functions without TLS. Any deployment reachable by hostname or public address would require HTTPS, and would additionally require the access controls that are explicitly out of scope (§2.3.2, §14.4).
