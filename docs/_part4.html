8Detailed Design

8.1 Configuration Subsystem

src/config.py defines a single frozen dataclass, Config, holding every tunable parameter in the system. A module-level singleton CONFIG is constructed at import time from Config.from_env(), which reads the process environment after python-dotenv has loaded any local .env file.

Three properties of this design matter. First, immutability: the dataclass is frozen, so configuration cannot drift at runtime. Second, typed coercion with diagnostics: helper functions _env_int, _env_float and _env_bool convert string environment values and raise a ValueError naming the offending variable if conversion fails, rather than failing obscurely later. Third, testability: from_env() is a classmethod, so tests construct isolated instances after manipulating the environment without mutating the global singleton.

The refactor that introduced this module replaced scattered os.environ.get() calls previously duplicated across five modules. Backwards compatibility was preserved deliberately: the environment variable names are unchanged, and pipeline.py retains module-level aliases (SAMPLE_RATE, OLLAMA_URL, and others) that now resolve to CONFIG values, so existing call sites in cli.py and chat_web.py required no modification. This confined the change to where configuration is read, not to how it is used.

8.2 Audio Capture and Endpoint Detection

pipeline.capture_audio() opens a raw 16-bit input stream at 16 kHz and consumes it in 30 ms frames (480 samples), the frame size required by the WebRTC VAD. A small state machine determines utterance boundaries:

StateTransition conditionAction
UntriggeredFrame classified as speechEnter Triggered; prepend the retained pre-roll buffer (10 frames, ≈300 ms) so speech onset is not clipped.
UntriggeredFrame classified as non-speechAppend to a bounded ring buffer; discard the oldest frame.
TriggeredFrame classified as speechAppend frame; reset the trailing-silence counter.
TriggeredConsecutive non-speech ≥ 800 msTerminate capture; return the accumulated utterance.
AnyElapsed time > 15 sTerminate capture unconditionally (FR-1.5).

An utterance containing fewer than 150 ms of speech frames is discarded as spurious rather than transcribed. Captured int16 samples are converted to float32 normalised to ±1.0 for the recogniser.

8.3 Audio Preprocessing

8.3.1 Amplitude normalisation

Normalisation targets a fixed RMS level of 0.1 rather than a fixed peak. RMS was chosen deliberately: peak normalisation is driven by the single loudest sample, so a whispered clip containing one incidental transient would be scaled as though it were loud, whereas a shouted clip is loud throughout. RMS reflects sustained perceived loudness, which is the property that actually differs between whispered and shouted delivery.

Two safeguards apply. Input whose RMS falls below 10−6 is passed through unmodified, avoiding division by near-zero and the consequent amplification of the noise floor. After gain is applied, if the resulting peak would exceed 0.99 the signal is rescaled so that it does not clip — necessary because a very quiet input attracts a large gain factor.

8.3.2 Pitch and rate detection

Median fundamental frequency is estimated with probabilistic YIN over voiced frames, and flagged when outside 80–400 Hz. Speaking rate is estimated from onset density — detected onsets divided by clip duration — and flagged when outside 0.75–1.35 times a nominal reference rate.

Design status — corrections disabled

The corresponding correction stages (pitch shifting and time-scale modification) are implemented but disabled by default via ENABLE_PITCH_CORRECTION and ENABLE_SPEED_CORRECTION. Empirical evaluation demonstrated that applying them reduced recognition accuracy from 96.0% to 48.0% on real recordings. The detection and logging paths remain active because the metadata is diagnostically useful; only the audio-modifying step is gated. The full analysis is presented in §12.4, and the behaviour is protected by regression tests (§11.3).

8.3.3 Failure containment

The pitch and rate stages call into numba-compiled routines within librosa. Under memory pressure — with the recogniser, language model, and synthesiser all resident — that just-in-time compilation has been observed to raise MemoryError. Each stage is therefore wrapped in its own exception guard that logs the failure, records it in the preprocessing report, and returns the audio unmodified. A second guard in the orchestration loop catches anything that escapes the first. Preprocessing is an accuracy enhancement, never a precondition for a turn completing.

8.4 Speech Recognition and Device Selection

8.4.1 Verified device fallback

load_whisper_model() attempts GPU construction first, then executes a short trial transcription over 0.25 s of silence before returning the model. This ordering is not incidental. On Windows, WhisperModel(device="cuda") constructs successfully even when the CUDA runtime libraries cannot be loaded; the failure surfaces only on the first genuine inference. Validating by construction alone would therefore have produced a system that appeared healthy at start-up and failed on the user’s first utterance. The trial inference converts that latent fault into a deterministic start-up check, after which the loader falls back to CPU with an int8 compute type. The same pattern is applied in verify_setup.py and benchmark.py.

8.4.2 CUDA library resolution on Windows

src/cuda_dlls.py exists to solve a specific, non-obvious platform defect. The CTranslate2 backend requires cuBLAS and cuDNN. On Linux the corresponding nvidia-*-cu12 wheels are sufficient on their own, because the shared library carries an RPATH referring to them. Windows has no RPATH equivalent, and CTranslate2 resolves these libraries through a plain LoadLibrary call — which does not consult directories registered via os.add_dll_directory(), the conventional remedy for this class of problem. That approach is silently ineffective here.

The module therefore locates each installed nvidia.* package, derives its bin directory, and prepends it to the process PATH before faster_whisper is imported anywhere. Every entry point that loads the recogniser calls this function ahead of the relevant import. Without it, the observed failure is RuntimeError: Library cublas64_12.dll is not found or cannot be loaded at first inference.

8.4.3 Two-pass decoding

transcribe() performs a single decode at a caller-supplied beam size, returning both the joined text and the raw segment objects, which carry the log-probabilities the confidence layer requires. transcribe_with_confidence() composes this with the gating policy: a fast first pass at beam 1, and — only where the first pass is judged insufficient — a second pass at beam 5. The wider search is thus paid for only when it is needed, rather than on every utterance.

8.5 Confidence Decision Layer

8.5.1 Score aggregation

The recogniser reports avg_logprob per segment. These are combined into a single utterance score as a duration-weighted mean, so that a long confident segment is not outweighed by a short uncertain one. An utterance producing no segments returns −999.0, a sentinel far below any plausible threshold, ensuring that silence or undecodable audio is always rejected rather than accidentally accepted.

8.5.3 Threshold selection and calibration

The default threshold is −0.6. avg_logprob is not a calibrated probability, so the value was chosen from observed behaviour on this project’s own recordings, where three bands were consistently apparent: above −0.5 the recogniser was essentially always correct; between −0.5 and −0.9 it was unreliable; below −0.9 it was typically wrong. Representative values observed during system testing were −0.29 for a clean utterance, −0.60 for a borderline case that was accepted on the second pass, and −0.85 and −0.88 for inputs correctly rejected.

Calibration guidance

This distribution shifts with speaker, microphone, and acoustic environment. The confidence_log.csv audit trail exists precisely so the threshold can be re-tuned from evidence: too many spurious repeat requests indicates the threshold should be lowered (more negative); incorrect transcriptions reaching the model indicates it should be raised. This is a known limitation and a documented fairness consideration (§15.3).

8.5.4 Audit trail

Every decision — including every acceptance — appends one row to confidence_log.csv, recording UTC timestamp, transcribed text, score to four decimal places, threshold in force, decision, beam size used, and attempt number. Logging acceptances as well as rejections is deliberate: a log of failures alone cannot establish a false-rejection rate.

8.6 Language Model Integration

8.6.1 Response shaping

A system prompt constrains responses to one to three plain conversational sentences and prohibits lists, headings, and markup. This is not stylistic preference but a functional requirement of the medium: every response is read aloud, where a numbered list becomes an unstructured monologue with none of the visual scaffolding that made the structure useful. During model comparison it emerged that this prompt constraint improved spoken suitability far more than the choice of model did — both candidate models produced structured, list-heavy output without it, and concise spoken prose with it (§12.6).

8.6.2 Transport and context

Two integration paths exist. pipeline.generate_response() targets the single-turn completion endpoint and is used by the terminal interface. The browser interface instead proxies the chat endpoint through chat_web.respond_endpoint(), supplying the system prompt followed by the trailing window of conversation history (bounded at twelve messages, approximately six exchanges) and the new user message. This gives the browser interface genuine multi-turn memory, which the terminal interface does not have — a deliberate asymmetry, since the browser client can hold session state that a stateless terminal loop cannot.

Both paths stream. Tokens are relayed to the caller as they arrive rather than buffered until completion, so perceived latency is governed by time-to-first-token.

8.6.3 Retry semantics

Connection failures are retried up to twice with linear backoff, but only under a specific condition: no output may yet have been delivered to the caller. Once a partial response has reached the user, restarting the request would duplicate content that has already been displayed or spoken, so the failure is surfaced instead. This condition is tracked explicitly in both implementations.

8.7 Speech Synthesis

synthesize_speech() invokes the Piper executable as a subprocess, writing the text to standard input and receiving a WAV file at a specified path. The executable is located relative to sys.executable rather than relying on PATH, because the console script is installed alongside the interpreter in the virtual environment and is only on PATH if that environment has been activated in the calling shell. Resolving relative to the running interpreter makes invocation work identically whether or not the environment was activated — a concrete robustness improvement that removed a real class of setup failure. A non-zero exit status raises a RuntimeError carrying the captured standard error.

8.8 Web Layer

8.8.1 Shared concerns

web_common.py supplies both Flask applications with identical error semantics and serving behaviour. Handlers for 400, 404, 413 and 500 return a uniform {"error": "..."} JSON body in place of Flask’s default HTML error pages, so a programmatic client receives a parseable response in every case, and internal paths or stack traces are never disclosed. run_app() selects between the Flask development server and Waitress according to CONFIG.production, allowing a production-grade WSGI server to be used without any code change.

8.8.2 Conversational service

chat_web.py exposes four endpoints (§10.1). The recogniser is loaded lazily on first transcription rather than at import, so start-up is immediate and a model-loading failure presents as a clear HTTP error rather than a server that never becomes ready. Request bodies are capped at 25 MB. The transcription endpoint mirrors the orchestration core exactly — it calls the same normalize_audio() and transcribe_with_confidence() functions the terminal interface uses, including the identical preprocessing fallback guard — so the two interfaces cannot diverge in behaviour.

8.8.3 Dataset recorder

record_web.py serves the recording interface and maintains the dataset manifest. The plan endpoint returns the full grid of word and modulation pairs annotated with completion state derived from the manifest, enabling the interface to resume at the first incomplete pair after an interruption. Uploads are decoded, validated for minimum duration, written as 16 kHz mono WAV, and the manifest row is replaced idempotently so that a re-recording overwrites rather than duplicates.

8.9 Error Handling Strategy

The governing principle is that enhancement failures degrade silently while dependency failures are surfaced explicitly and actionably.

9.3 Design Rationale — No Database

The system uses flat files exclusively. This is a considered decision rather than an omission. The data volumes are trivial (tens of rows), the access patterns are append-only or whole-file, and every persistent artefact benefits from being directly inspectable — the audit log and benchmark results are evidence intended to be read by a human, opened in a spreadsheet, or version-controlled. A database would add an operational dependency and a schema migration burden for no functional gain at this scale. The consequence is accepted and recorded: there is no durable conversation history (§17).

9.4 Retention

Nothing is deleted automatically except through log rotation, which retains approximately 20 MB of pipeline logs across four generations. The confidence log grows without bound and contains transcribed speech; §15.2 addresses the resulting retention obligation, and §17 records it as a known limitation.

11Verification & Validation

11.1 Strategy

Verification operates at three levels. Automated unit and integration tests cover deterministic logic — confidence arithmetic and decisions, configuration parsing, HTTP endpoint contracts, and signal-processing invariants. Manual system testing covers behaviour that requires real hardware: microphone capture, GPU inference, model serving, and audio playback. Empirical measurement (§12) covers the accuracy claims, which cannot be established by testing alone because they are statements about a model’s behaviour on real data.

A deliberate constraint governs the automated suite: it must run with no GPU, no model server, no microphone, and no synthesis binary. Every external interaction is mocked at its call site. This keeps the suite fast, deterministic, and executable on ordinary continuous-integration infrastructure — at the cost, honestly acknowledged, that it verifies the system’s logic rather than its integration with those external components. Integration is covered by §11.5.

11.3 Regression Tests of Record

Evidence lock-in

Two tests in tests/test_preprocessing.py exist specifically to prevent the defect described in §12.4 from recurring. Each forces the detection stage to report a clear outlier — an implausible fundamental frequency, or a single onset across a long clip — and then asserts that the corresponding correction function (pitch_shift, time_stretch) is never invoked and that the returned audio is bit-identical to the input. They also assert that both feature flags remain False.

The intent is procedural as much as technical: re-enabling either correction now requires deliberately editing a failing test, which forces the change to be justified against new measurement rather than made casually.

11.4 Continuous Integration

The workflow at .github/workflows/tests.yml executes on every push and pull request. It provisions Python 3.11 on ubuntu-latest, installs requirements-dev.txt — deliberately not the GPU requirements, since roughly 1.3 GB of CUDA wheels serve no purpose where every GPU path is mocked — then runs ruff check . followed by pytest -v. Lint findings and test failures both fail the build.
